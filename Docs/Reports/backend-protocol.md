# Backend host protocol implementation (hardware-free)

Primary source: [rashevskyv/dbi `dbibackend` at `22090afc64cc7b5d645a99bf3d4d8625a67b766e`](https://github.com/rashevskyv/dbi/blob/22090afc64cc7b5d645a99bf3d4d8625a67b766e/dbibackend), inspected as the complete raw script. This is an independent implementation and description, not a redistribution of that script; its license has not been determined. DBI 647 interoperability and actual device ACK fields are **unverified**.

The script uses a 16-byte little-endian header: ASCII `DBI0`, UInt32 type (request=0, response=1, ACK=2), UInt32 command (EXIT=0, FILE_RANGE=2, LIST=3), UInt32 payload length. Legacy LIST=1 is declared but not processed, so rejected. The host receives requests. LIST (zero request payload) replies with a response header whose length is the UTF-8 byte length of newline-terminated basenames in offer order; for a nonempty list it waits for a LIST ACK header before sending bytes. Empty lists have no ACK/payload stage. FILE_RANGE receives a request header with payload length, sends an ACK echoing that length, then reads `UInt32 range size, UInt64 offset, UInt32 name byte length, UTF-8 name`; replies with response header whose length is the requested size, waits for a FILE_RANGE ACK header, then sends raw file bytes. EXIT (zero request payload) receives an empty response and ends the host loop. The reference script reads only 16 bytes of each response ACK, does not check its fields, and does not establish a required echoed-size or ACK payload contract. This implementation checks magic/type/command and bounds the ACK length field without asserting it equals a previous length or reading an ACK payload. Nonzero ACK length remains a compatibility uncertainty. The script does not contain a host destination-selection command; SD/NAND is device-selected. EXIT is not an installation-success report.

`BackendSession` owns an explicitly supplied open transport and calls close exactly once on success, error or cancellation. It is one-shot, rejects reentry/reuse, and never reconnects. Failed close yields `releaseUnverified` and forbids reuse, including when the protocol body succeeded; successful close preserves the original operation/observer error. Offer names must be nonempty newline-safe UTF-8 basenames (no path separators, colon or controls), with unique exact UTF-8 bytes and unique IDs; a request matches only an offered name. Range arithmetic checks overflow and offered source-size bounds before reading; byteCount is source size metadata, not content verification. Default maximum command/list payload is 65,536 bytes, maximum data chunk 65,536 bytes, operation timeout 5,000 ms, session budget 120,000 ms, command budget 4,096. Configured caps cannot exceed 1 MiB payload/chunk and 100,000 commands. Fragmented reads are reassembled with bounded allocation; empty reads, malformed UTF-8, short source reads and invalid ACKs fail closed. Unique-byte interval coverage, not sum of retransmissions, controls per-file phase; totalBytesSent includes retransmissions. Full coverage only means `transferredAwaitingConfirmation`, never installed. A zero-byte file remains `notRequested` if no range was requested.

Progress integration: `public typealias BackendProgressObserver = @Sendable (BackendTransferResult) async throws -> Void`; call `try await session.run(offers: offers, onProgress: { snapshot in ... })`, or omit the optional callback for the original API. After each successfully completed host file-data write, the callback receives a conservative, offer-ordered snapshot with unique coverage, total host file bytes (including repeated transfers), and `peerRequestedExit == false`. Full coverage gives only `transferredAwaitingConfirmation`, never installed; the final result after EXIT has `peerRequestedExit == true`. If observer persistence throws, the session stops and attempts a single close, preserving the observer error if close succeeds. The callback is serially awaited before another command/chunk. A crash after successful transport write but before durable callback completion leaves the transferred bytes unknown to the journal; this API does not provide exactly-once transfer or durable device commit. Conversely, callback success does not attest the peer installed or retained content. A non-cooperative observer also limits the hard deadline guarantee.

Follow-up validation: `swift test --filter BackendProtocol` passed **10 fake-peer tests** (zero failures), and `swift build` completed; shell commands propagated their actual exit status rather than masking failures behind a pipeline. No actual device, USB client or source package was read.

**Deadline caveat:** the monotonic session deadline is checked before/after each I/O and source read and finite timeouts are passed to the transport. Swift cannot forcibly interrupt a transport or reader that ignores cancellation/timeouts; close occurs when that awaited operation returns. The transport contract must enforce its own finite I/O timeout. No hardware, NAS/source package, USB enumeration/open, dependency installation or other client was exercised here. All observed behavior is fake-peer evidence only.
