# Backend allowlisted reader and transfer journal

## Reader

`AllowlistedBackendFileReader.open(bindings:)` accepts explicit opaque IDs, file URLs, and expected UInt64 sizes; it validates and records device/inode/size/mtime/ctime metadata without reading bodies. The actor conforms to `BackendFileReading` and serves only positive ranges up to 1 MiB and within the bound file's size, with subtraction-based overflow-safe range checks. Each read opens every directory component with `openat(O_NOFOLLOW | O_DIRECTORY)` and the final path with `O_NOFOLLOW | O_NONBLOCK`, then rejects anything not a regular file before reading; this avoids a FIFO-without-writer open hang. Literal NUL path bytes are rejected before C-string conversion; Foundation percent-encodes NUL when constructing a file URL on this platform, so that fixture confirms no truncated-path alias rather than exercising the literal-NUL branch. Binding preparation checks cancellation before and between files. Trusted temporary test roots are explicitly resolved so macOS `/var` symlink does not weaken ancestor-symlink rejection; it checks evidence before and after a single `pread` and reopens the path to detect replacements. Unknown IDs, symlinks (including ancestor symlinks), replacement, size or timestamp changes, cancellation and short reads fail closed. No ID is parsed into a path. The factory awaits an actor method to avoid doing blocking metadata work on MainActor.

POSIX metadata is not cryptographic content identity. Timestamp/inode reuse, deliberately restored timestamps, races after final validation, remote filesystem metadata caching and SMB disconnect behavior cannot be ruled out here; later transfer integration must revalidate evidence and treat uncertainty as failure. `pread`, `openat`, `fstat` and SMB kernel operations can block despite actor isolation or task cancellation; there is **no enforceable hard deadline** for a blocked filesystem syscall. This worker did not read real NAS package contents; tests read tiny temporary fixtures only.

## Journal

`BackendTransferJournal.open(at:)` loads a bounded (1 MiB, at most 128 attempts and 4096 files per attempt) local schema-1 Codable document. `begin(id:offers:)`, `record(_:attemptID:)`, and `end(attemptID:state:)` serialize per-attempt progress through an actor; `record` accepts full `BackendTransferResult` snapshots from a future observer and validates IDs, lengths, phase/byte consistency, monotonic coverage and totals. It preserves previous attempts; failed and interrupted attempts keep partial coverage. On process restart every active attempt is atomically marked interrupted; no automatic resume, retry, installation promotion, device identifier, source URL or secret is stored. Full host byte coverage is only `transferredAwaitingConfirmation`, not installed. Unknown schema, corrupt, symlinked, FIFO or oversized files raise `recoveryRequired` and are not overwritten; the bounded loader uses nonblocking open so a raced FIFO cannot hang before `fstat`. A progress update cannot increase unique coverage by more than the increase in total host bytes, even if prior total included retransmissions. `finished` requires a recorded peer EXIT but may still contain partial files; persisted finished-without-exit and multiple active attempts are rejected. Timestamps never regress on wall-clock rollback. Opaque IDs are retained as given and may themselves contain paths; they are never interpreted as filesystem paths or deliberately stripped.  recovery requires a user-reviewed copy/decision. Use one owner per journal path (no cross-process locking is claimed).

Each commit creates a mode-0600 temporary file in the same directory, writes and `fsync`s the file, atomically renames over the journal, then `fsync`s the directory; in-memory state advances only after successful persistence. If the post-rename directory sync fails, the actor fences further changes because disk state may be uncertain. An internal-only after-rename fault hook deterministically verifies the fence and preservation of a complete on-disk replacement without claiming disk durability. The atomic rename provides either old or new complete file after a process crash under normal local-filesystem semantics. The fsync sequence requests local durability against an OS/power crash where filesystem and storage hardware honor those operations; it is not a guarantee against lying controllers, remote/network filesystems, external backup corruption, or concurrent journal owners. No App UI invokes these APIs and no USB operation is introduced.

## Validation

Prior scoped `swift test --filter 'BackendPreflight|BackendFileAccess|BackendJournal'` passed 17 tests across three suites. This correction ran `swift test --filter 'BackendFileAccess|BackendJournal'` (15 tests across two suites passed) and `swift build` (passed) in the isolated worktree. FileAccess tests cover exact slices, opaque IDs, missing/stale/unknown sources, symlink ancestors and replacement, range overflow and cancellation. Short reads during a single tiny local `pread` are inherently race-dependent; implementation maps them to `shortRead` after metadata checks, with no fabricated deterministic hardware result. Journal tests cover round trip and atomic replacement, restart interruption, invalid transitions/snapshots, concurrent updates and corrupt/unknown schema preservation. No full suite/RealNASScanTests, GUI or hardware validation was repeated in this dispatch. See `backend-preflight.md` for the correction to the previous full-test NAS evidence.
